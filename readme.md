# Task1. Проектирование технологической архитектуры

**основные требования**:

1. Развитие сервиса во всех регионах РФ, клиенты из всех часовых поясов
2. значительный рост количества пользователей и запросов
3. бесперебойная работа сервиса 24/7
4. RTO — 45 мин
5. RPO — 15 мин
6. доступность  99,9%
7. одинаковое время загрузки страниц для пользователей из разных регионов

На текущий момент сервис хранит ограниченный набор данных, который включает в себя:

  -  базовую информацию о клиентах — ФИО, контакты, документы,
  -  информацию о продуктах и тарифах
  -  историю заявок клиентов.

Общий объём данных, которые хранятся в системе, равен 50 GB.

Вопросы к схеме и ответы:

- вертикальное и горизонтальное масштабирование.
Требуется ли использование дополнительных зон безопасности?

1. Основные требования к приложению, это быстродействие при максимальном географическом охвате.
Стратегия горизонтального масштабирования напрашивается сама собой.
О вертикальном можно будет говорить, если мощностей конкретного ЦОД не будет хватать для обеспечения работоспособности приложения при переводе траффика с неработающего ЦОД  

a. Будут использоваться независимые кластеры Kubernetes для обеспечения независимости и отказоустойчивости системы.
b. Используем GSLB для геораспределения нагрузки по latency при запросах с ЦОД
c. Так как уже предполагается использование геораспределенных ЦОД, то разумно с помощью них реализовать active-active стратегию. ЦОД заведомо предполагаются всегда работающими для уменьшения времени запросов от пользователей из удаленных регионов. Так что необходимо только настроить репликацию данных между ЦОД 
d. Предполагаю делать репликацию данных в соседние ЦОД 

В моем решении ЦОД разбиты географически, логично было бы использовать геошардирование, но тогда будут фозникать проблемы с пользователями перемещающимися по стране. Необходимо реализовывать либо пользовательскую привязку к конкретному ЦОД, либо отказываться от геошардирования и реплицировать данные асинхронно по всем ЦОД.
Я выбрал второй путь.

- используем Patroni кластер для управления PostgreSQL базами
- дополнительно сохраняем бэкап баз с помощью pgBackRest
- как уже указывал ранее для восстановления из бэкапа (50ГБ за 15 мин max) необходимо иметь соединение между бэкап сервером и DR сервером не ниже 450 мбит/сек, а желательно гигабитное давая время на запуск

 # Task4. Проектирование продажи ОСАГО

 **Предусловия**:

- Пользовательский путь: клиенту предлагается заполнить заявку с информацией о своём автомобиле, после этого сервис запрашивает у всех доступных страховых компаний предложения с условиями страхования под заявку клиента. 
  - Все страховые компании предоставляют однотипные REST API с двумя эндпоинтами:
    - создать заявку на ОСАГО
    - получить предложение по заявке.
- предложения от каждой страховой компании отображались сразу, как только от неё пришёл ответ
- Максимальное время ожидания решения от страховой компании — 60 секунд. 
- в пик нагрузки количество одновременных пользователей, создающих заявку на ОСАГО, может достигать 2,5 тысячи человек

 **Технические предусловия**:
- Сохранить подход, который использовался для получения данных о продуктах и тарифах из страховых компаний
- Выделить отдельный сервис для взаимодействия со страховыми компаниями — osago-aggregator. 
  - Функциональная обязанность этого сервиса — отправка заявок в страховые компании и дальнейший опрос решений по ним для передачи результатов в core-app.
- Остальная функциональность, связанная с оформлением ОСАГО, остаётся на стороне бэкенда в core-app

### Предлагаемое решение:

**Схема продажи ОСАГО**:
![Схема продажи ОСАГО](Task4\InsureTech_C4_сontainer-diagram_to_be.png)

**Описание решения**:


1. Новые объекты на схеме:
-  Поднимаем новый сервис osago-aggregator 
-  с key-value базой (например Redis) osago-aggregator-db
  
2. Интеграции:
- Фронтенд приложения <-> сore-app
  - Создание запроса на ОСАГО - REST 
  - получение обновлений по предложениям от страховых компаний - WebSocket (так как требуется немедленность отображения)
- сore-app <-> osago-aggregator
  - запросы ото всех пользователей после попадания в core-app насыщаются необходимыми данными и публикуются в соответсвующий топик в Kafka брокере
  - osago-aggregator подписан на топик с новыми запросами на ОСАГО. 
    1. Получает запрос из брокера
    2. формирует запись в своей KeyValued DB в статусе *создано*
    3. формирует запросы к внешним АПИ для создания заявки на ОСАГО
    4. меняет статус на *отправлено* с указанием времени отправки 
    5. формирует запросы к внешним АПИ для обновления статусов
    6. при получении предложения от внешнего АПИ обновляет статус на *обработано*, формирует сообщение в соответствующий топик брокера и затирает запись в KeyValued DB
    7. при отсутвии ответа от внешнего АПИ в течение 60 сек начиная со времени отправки обновляет статус на *просрочено*, формирует сообщение в соответствующий топик брокера и затирает запись в KeyValued DB

3. паттерны отказоустойчивости:
- Фронтенд приложения <-> сore-app:
  - Если мы знаем предельно возможное количество RPS по заявкам на страховки, то можем использовать технику Rate Limiting на REST запросы на создание заявок на ОСАГО
- сore-app <-> osago-aggregator
  - в предлагаемой схеме реализовано асинхронное взаимодействие через брокер. Дополнительные средства повышения отказоустойчивости не требуются
- osago-aggregator <-> Системы страховых компаний
  - Данная интеграция потенциально самая проблемная. Мы не можем управлять внешним АПИ поэтому приходится рассчитывать только на свои внутренние методы отказоустойчивости
    - Предлагаю реализовать Retry для запросов к внешнему АПИ завершившихся ошибкой (пока они внутри допустимого  интервала в 60 сек)
    - Timeout у нас напрямую заложен в требованиях
    - Circuit Breaker можно использовать для случаев падения сервисов внешнего АПИ 

**Общие замечания к решению**: 
Предполагаю что при указанной нагрузке сразу необходимо закладывать логику горизонтального масштабирования в сервис osago-aggregator. Также возможно CQRS разделение инстансов сервиса на группу сервисов которые будут только создавать заявки и те которые будут заниматься обновлением статусов.

В шардировании KeyValued DB смысла не вижу. Так как количество одновременных записей предполагается порядка нескольких тысяч при пиковой нагрузке, что не очень много.

При репликации (в том числе при CQRS реализации) необходимо уделить внимание конститсентности статусов заявок
